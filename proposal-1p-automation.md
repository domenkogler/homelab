> **Context:** Your intent — "everything is known in the SSOT (`deployment-secrets.md`); automate creation of the 1Password items; only values that can only be generated manually should stay deploy-gated."

## 1. Is this feasible? — Yes, but with two constraints

The SSOT **defines** every item (name + `<type>` + field layout + consumer), so *existence and shape*
are fully derivable. Two hard constraints prevent 100% automation:

1. **Item *existence* is automatable; the *value* is not always.** The SSOT is a *schema* — it says
   `openrouter_api` is an API Credential consumed by LiteLLM. It does **not** contain the OpenRouter key,
   the Cohere key, the SMTP password, the netcup password, the MikroTik admin password, the ISP PPPoE
   password, the Authentik bootstrap admin password, etc. Those are **external / human-known** facts that
   cannot be invented by a computer.
2. **Many values are produced *by* other parts of the deploy** (not pre-createable at all):
   - Authentik OIDC client creds (8 `_oidc`/`openwebui_api`/`matrix_api`/`headscale_api` items) — the
     client_id/secret **are created by the Authentik Blueprint** (HD-143 glue writes them back). You
     cannot pre-generate these; they must exist before fill.
   - `authentik-api_token` / `authentik-provision_api` — tokens **issued in the Authentik UI** (after
     Authentik is live), not by us.
   - `openclaw_gateway_token` — generated by `openclaw onboard` at deploy.
   - `authentik-ldap_bind` — populated when the LDAP outpost is created.
   - `ha-api` — a long-lived HA token, created in the HA UI.
   - `openclaw-opencloud_api` password — an app-specific password created in the OpenCloud UI.

## 2. The automation can create the *skeleton* for every item

A script driven by the SSOT can **create every item that does not yet exist**, with the correct
**name, 1Password item type, vault, and the correct empty/filled fields fireshape**, and set the
fields whose values are internally generatable. That gives you:

- **Idempotent**: `op item get` → if absent → `op item create` with the right template. Re-run safe.
- **Right shape from day one**: correct item type (Login / Password / API Credential / Database /
  SSH Key) + correct `field=` names — no manual item-by-item creation, no "which type was this again".
- **No secrets written to repo**: script lives in `scripts/` (or an Ansible role `secrets_provision`),
  values come from `op` at runtime; the only thing in Git is the item *catalog* + the generator.

## 3. Value-origin classification (what the automation CAN do per item)

Derive this table directly from `deployment-secrets.md`:

| Origin class | Meaning | Can the script populate? |
|--------------|---------|--------------------------|
| **generated** | value = random, computable, no external knowledge | ✅ Yes — `op generate` / deterministic |
| **external** | value is known only outside Git (key, password, token) | ❌ No — must be pasted by hand once |
| **derived-from-deploy** | value is *created by another service during deploy* (OIDC creds, Authentik/HA/OpenCloud tokens, `openclaw` gateway token, LDAP bind) | ❌ No — filled later by the deploy itself (secret-egress glue, outpost, `onboard`) |

| `derived-from-deploy` items **cannot even be "created"** — they are *populated by a later step*, not pre-provisioned. | | |

## 4. Where the write-capability comes from (RESOLVED: interactive one-shot `op signin`)

`community.general.onepassword` **lookup** only *reads*. Creating items needs a *write-capable path*.

**Decision — interactive one-shot `op signin` (option c).** An interactive `op signin` authenticates
with Domen's **personal account** (biometric/2FA), which already has **write** on the `Homelab-ansible` vault — so
**no new credential surface is introduced** beyond a short-lived laptop session. This is strictly better
than minting a write-scoped Service Account for the job.

Caveats to make "one-time" real:
1. **The SA-token env var overrides it.** `~/.bashrc` sources `OP_SERVICE_ACCOUNT_TOKEN` (read-only SA).
   When set, `op` authenticates as the SA — **not** your interactive session — so the provisioner would
   silently have no write. The provision step must run with `OP_SERVICE_ACCOUNT_TOKEN` unset (or pass
   an explicit `op --session` token captured from `op signin`).
2. **The session is cached.** `op signin` caches a local session until expiry or `op signout`. "One-time"
   therefore requires the runbook to end with **`op signout`** (put it in the provisioner's `finally`).
3. **Laptop-bound, not headless.** Great for *bootstrap-time pre-seeding* (your goal). It **cannot** run
   inside Forgejo Actions / the Ansible deploy path. If mid-deploy provisioning is ever needed
   headlessly, you'd revisit a write-scoped SA afterward.

Tradeoff stated honestly: **interactive signin = one-time laptop seed; SA write-token = repeatable and
headless.** Because the ask is "create items whose values are known now, only manual ones deploy-gated,"
interactive fits.

> The Service-Account write path is **discarded** (it was the earlier Option a/b). Stored here for the record:
> the runner's `Service Account Auth Token: ansible` (Private vault, `docs/1password.md §1`) is read-only on
> `Homelab-ansible`; a separate write-scoped SA (`provisioner`) would be the repeatable/headless alternative if
> mid-deploy provisioning is ever needed later.

## 5. Proposed mechanics (not yet built)

**Option A (recommended): `scripts/provision-secrets.py` — a catalog-driven, interactive `op` loop on the laptop.**

1. **Catalog source — `group_vars/all/secrets.yml` (RESOLVED Q3).** Secrets themselves never go in group_vars;
   only the **item catalog (metadata)** does, exactly like `group_vars/all/versions.yml` (HD-156 pattern): a
   machine-readable list of every item — `name`, `type` (login/password/api/db/ssh/oidc), `field(s)`,
   `source` (generated/manual/derived) + a `vault` flag.
   - **group_vars linter role:** `validate-secrets.py` must **exempt** the `secrets.yml` `field:` values
     (`credential`, `password`, `bcrypt_hash`) from its literal-credential lint, else it would false-red on
     words that are *field names*, not secrets.
   - **Linkage:** `deployment-secrets.md` is **derived from / cross-checked against** `group_vars/all/secrets.yml`
     (IaC-as-SSOT, `.md`-as-render — consistent with the rest of the repo). `validate-secrets.py` plus a
     tiny catalog-vs-md check flag drift. `scripts/provision-secrets.py` reads only the catalog.
- **Script actions (idempotent, `op` interactive):**
  1. `op item get <name>` — nothing if present (always skip `derived`; skip `manual` value-fill).
  2. `generated` → `op item create` with `op generate` password (and username where it has one).
  3. `manual` → `op item create` with the correct item type + an empty placeholder `field` (never a fake value).
  4. Emit a **provision report** (created-empty / filled / needs-human) → checklist + `deployment-tasks` row state.
  5. **End with `op signout`** (bake it into the `finally`) / re-assert `OP_SERVICE_ACCOUNT_TOKEN` cleared.
- **Fail-closed / no false-live:** never mark a `manual` item "created" as if it had a value.


## 6. Where SSH keys fit (they are the seed, not routine)

The three `_ssh` items are special: they must exist **before** any host provisioning (post_install injects
keys) and their 1Password SSH agent needs `~/.ssh/*.pub` reference files. Recommend:
- Generate the three ED25519 pairs **once at bootstrap** (laptop-side, interactive) — per `docs/deployment-secrets.md`
  → SSH Key Separation. This stays a **manual/one-time** step (a script can auto-generate + fill them, but on a
  new laptop it's a trusted hand action). Then everything else can be automated.
