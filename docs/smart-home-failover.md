> **Role:** Detail — active/standby HA failover to oldsrv, takeover + reverse (failback) runbooks, DNS redundancy tie-in.
> **Links to:** `smart-home.md`, `network-dns.md`, `network-vlans.md`,
> `deployment-ansible.md`, `services.md`, `backup.md`
> **Linked from:** `smart-home.md`, `index.md`

> 🔴 **The standby is UNDEPLOYED — not "cold-deployed", absent — and no takeover has ever been drilled.**
> Measured 2026-10-19 (§Intent vs reality below): oldsrv runs 39 containers and none of them is
> `home-assistant-standby` or `keepalived`, running or stopped; the rendered compose pins
> `home-assistant:2026.9.4` while the host holds only `2026.8.1`/`latest`, so `compose up` has never been
> run against the current render. What DOES exist is the rendered cold target — `/opt/home-assistant-standby`
> with its compose, `configuration.yaml`, `secrets.yaml` and the keepalived variants — and the Pi → standby
> config push, which is **live on the Pi** (`ha-config-sync.timer`: enabled + active, ~15 min, last tick
> `Finished`). It reads `not-found` on oldsrv because the pusher is the SOURCE, and that is the correct read
> — the same trap as `systemctl is-active keepalived` there.
>
> **The design this was meant to serve, unchanged.** `home-assistant-standby` carries `enabled: false` in
> the oldsrv registry so the `docker_services` deploy loop never touches it; the `home_assistant` role owns
> the whole cold target — renders the compose + configs, bootstraps the active `keepalived.conf` from the
> BACKUP variant (`force: false`, Pi-pattern) so the bind-mount is a real file from render time, and creates
> the container with `--no-recreate` so a takeover does not depend on a registry being reachable. Nothing
> starts it: `restart: "no"` and no unit mean **the cold node is only ever raised by the takeover path**.
> Because the standby compose hosts oldsrv's keepalived, while it is down the `ha-vip` has exactly **one
> advertiser — the Pi**: the VIP never floats on its own and "HA failed over" is always a human act.
>
> **What happens today if you click a failover card.** `ha-failover.sh forward` would not start a standby,
> it would **create one in production while the VIP is already moving**: `promote_vip()` runs
> `docker compose … up -d keepalived` on a service that does not exist yet — creating and starting the VRRP
> container, so the VIP arrives on oldsrv beside a Pi that still advertises it — and then runs
> `up -d home-assistant` for a service whose pinned tag is **not on the host**, so the takeover waits on a
> registry pull and fails outright if the registry is unreachable, which is exactly the outage-shaped moment
> this path exists for. `reverse` (`down --remove-orphans` + demote) then tears down the container the
> forward leg just created. Neither direction has been executed once, from either side.
>
> **What would have to be created for the click to work.** (1) the cold create, run once in an owner window
> — `ansible-playbook IaC/ansible/playbooks/home_servers.yml --limit oldsrv --tags ha_failover` (⛔ never
> `--diff`; its `authorized_key` task writes SSH keys on oldsrv) — which renders and creates with
> `--no-recreate` and starts nothing; (2) the pinned image on the host before any drill, so a takeover never
> depends on a registry; (3) a forward drill, a reverse drill, and the standby KNX tunnel read (HD-434).
> Until (1) runs the two **Homepage failover cards are rendered** (`homepage_failover_button: true`,
> generated by
> [`../IaC/ansible/templates/homepage_services.yaml.j2`](../IaC/ansible/templates/homepage_services.yaml.j2))
> and they are the same `/usr/local/sbin/ha-failover.sh` trigger behind root's `sudo … forward`, reachable
> from the home network only (§Forward Takeover, *Who fires it*) — so the launchpad currently offers a real,
> untested cold-create-under-pressure, not a standby start.
> Homematic has no local RF path; the HmIP-HAP stays cloud-mode
> ([smart-home-rejected.md](smart-home-rejected.md)). Runbooks below are the spec to be executed at
> takeover time.

## Goals & Non-Goals

### Must hold (non-negotiables)
- **No WAN dependency on the critical path.** Lights/covers toggling must keep working when the internet is down.
- **WAN loss is NOT a failover trigger.** HA is fully local — internet loss does not move HA. Failover is triggered only by **Pi failure** (power, SD card, OS crash, network path) and the *mechanism* simply must work while WAN is down.
- **Exactly one active HA node at a time** (no split-brain). Two HAs driving the same Shelly/KNX/ESPHome devices conflict; HA has **no native active/active clustering or state replication**.

### Scope
- Primary: Raspberry Pi 4 (`pi.kogler.si`; HA accessed via VIP, Home VLAN 10).
- Fallback: **oldsrv** (`home-assistant-standby` Docker container, cold by default).
- Supervision: **manual** trigger + **manual** failback (accepted design — no false negatives from automation).
- Stale state on takeover is acceptable: HA re-polls devices on startup (target: controlling again in 1–3 min).
- **Homematic IP has no local RF path**: there is no `HmIP-RFUSB` stick and no RaspberryMatic, so Homematic rides the cloud **HmIP-HAP** — nothing physical moves on takeover. KNX/Shelly are IP-based and fail over purely via the VIP with no physical action ([smart-home-rejected.md](smart-home-rejected.md)).

## Architecture Overview

```
   ┌─────────────────────────────┐
   │  MikroTik RB4011 (always on) │   also runs DHCP; router/switch
   │                             │   independent of both HA nodes
   └──────────────┬──────────────┘
                  │ route / DHCP / optional VIP contact
   ┌──────────────▼──────────────┐
   │      HA VIP (ha-vip)       │   stable address everything points to
   └──────┬──────────────┬───────┘
          │              │
   ┌──────▼─────┐   ┌─────▼─────┐
   │   Pi 4     │   │  oldsrv   │
   │ HA PRIMARY │   │ HA STANDBY│   cold — started on takeover
   └──────┬─────┘   └─────┬─────┘
          │ keepalived VRRP — VIP follows the active node
   devices / Traefik / Technitium DNS all point at the VIP
```

### Addressing: shared Virtual IP (VIP)

- HA gets a **floating VIP ** on the Home VLAN that moves between the Pi and oldsrv via **keepalived (VRRP)**.
- **Devices, Companion apps, Traefik's `ha` route, and Technitium DNS all point at the VIP**, never a node-specific IP.
- On takeover the VIP follows the active node → **no per-device reconfiguration and no DNS flip on failover**. This is the key that makes failover practical.
- **Firewall:** Home→IoT trusted-IP rules for MQTT/HA must reference the **VIP / an IP-set**, not a per-node IP, so the standby can reach Shelly/KNX after takeover (see `network-vlans.md`).

> ### HA access: **WAN-independent + local-auth — Authentik is never a gate**
>
> - **`ha` is NOT behind Authentik Forward-Auth** on either edge (`traefik-ha` Pi + `traefik` oldsrv carry
>   `# NOTE: no authentik-forward-auth@file middleware on the ha route`): the
>   Companion WebSocket/token flow breaks behind a proxy gate.
> - **HA authenticates locally** (`type: homeassistant`) — no Authentik in the `ha` path, no IdP and no WAN
>   between the house and its lights (decision log: [smart-home-rejected.md](smart-home-rejected.md)).
> - **`auth_providers` invariant:** always keep `type: homeassistant`. If `auth_providers` were ever set
>   to only `trusted_networks`/external, HA shows *"Enable mobile clients"* for any client from an
>   untrusted network (incl. tailnet CGNAT / cellular) and the app can't log in.
> - **Access matrix (home-only + tailnet):**
>   - Home WiFi: `https://ha.kogler.si` (`external_url` set; local login).
>   - Tailnet (away): Companion App via tailnet path (subnet route or tailnet DNS/`ha.ts.kogler.si` + ACL)
>     — local login, **no Authentik in the path**.
> - **Open:** (1) align + seed the Pi Technitium admin so `ha.kogler.si` → VIP resolves on ALL
>   3 DNS instances — it removes a DNS-ordering dependency (today the Pi zone is empty and the VPS primary
>   answers → VIP); (2) the mobile-over-Tailscale path (subnet router / tailnet DNS + ACL) —
>   **the transport exists, the app pointer does not:** the Pi is a tailnet node in its own right and its
>   `traefik-ha` edge answers `https://pi.ts.kogler.si/` → 200 over a DIRECT session, with no subnet routes
>   and no Authentik in the path. ⚠ Away from home the name that answers is `pi.ts.kogler.si`, not
>   `ha.ts.kogler.si` (see *Away access (tailnet)* below). Pointing the Companion App at it is
>   **per-device config — an owner step nothing in IaC can do**.
- **VRRP auth constraint:** keepalived uses `auth_type PASS` (an 8-char password from `ha-vrrp_password`, truncated identically on both nodes). VRRP has **no stronger in-protocol auth** — VRRPv2 offers only PASS (plaintext) or AH (discontinued), and VRRPv3 (RFC 5798) **removed Authentication Header entirely** — so `auth_type PASS` is the maximum the protocol provides, not an oversight to "fix" with a stronger cipher. The real mitigation is **network trust**: VRRP multicast runs only on the Home VLAN (10), isolated from the Management/IoT planes. Do not chase a "real auth mechanism" here (none exists); rely on VLAN isolation instead. (Likewise, the keepalived image is pinned to `keepalived_version` — never `:latest`.)

> ⚠ **VRRP requires a controllable host on both sides.** The Pi runs **Debian + HA Container**, which is what makes keepalived on it possible. If the Pi ever runs HA OS again, VRRP on it is not feasible → fall back to manual DNS/NAT steering (slower, still workable).

## Nodes & Deployment

| Node | Role | Deployment | VIP |
|------|------|-----------|-----|
| Pi 4 (`pi.kogler.si`) | **Primary** (active) | Debian + **HA Container** (home_assistant role) + **Technitium DNS** | owns the VIP (`ha-vip`) in normal mode |
| oldsrv | **Fallback** (standby, cold) | `home-assistant-standby` Docker compose, `enabled: false` in the oldsrv registry — rendered and created by the `home_assistant` role, never started by a deploy; same home_assistant role template | takes over the VIP on takeover |

- **Published ports are part of the VIP contract:** the standby compose publishes `8123:8123` (`VIP:8123` = HA for the Traefik edges + the Prometheus target) and `5683:5683/udp` (Gen1 Shelly CoIoT/CoAP). A standby that is reachable by VIP but has no published app port is not a standby.
- **Technitium runs on the Pi** (`pi.kogler.si`, a Debian host; `ha.kogler.si` = VIP); instance roles and forwarders are the DNS SSOT's business — see `network-dns.md`.

- **Identical config from one source:** both nodes render the **same `configuration.yaml`** from the repo (`use_x_forwarded_for: true`, `trusted_proxies: <Traefik>`), including the `owner` account.
- **Secrets via one renderer:** the `home_assistant` role renders **`secrets.yaml.j2`** into `/opt/home-assistant-primary/secrets.yaml` (Pi) and `{{ ha_standby_path }}/secrets.yaml` (oldsrv) — inline `community.general.onepassword` lookups, fail-closed, block-scalar. `configuration.yaml.j2` references the values via `!secret <name>` (single source; HA resolves at YAML load). Each node keeps its OWN 1Password-rendered copy: `secrets.yaml` is excluded from the Pi→standby config rsync (`ha-config-sync.sh.j2`). `ha_api` is NOT part of HA's secrets.yaml — the `monitoring` role writes the HA bearer to `/etc/prometheus/ha_token` under the `alloy_ha_exporter` gate.
- **Update policy:** **Renovate + `stable` tag** (controlled/gated: Renovate → PR → review → deploy). **No watchtower** — preserves primary/standby version parity and the repo's deliberate update gating.

**Three probes that read wrong on this host, all worth knowing before the next pass — one class, two instances:**

⛔ **The wrong-host read.** A systemd state or a file-presence probe answers about the box you ran it on,
and this contract has two boxes: the pusher lives on the SOURCE, the standby's VRRP lives in a CONTAINER on
the target. Both probes below came back empty, both were read as missing halves, and both readings were
correct about a host that was not the one owning the unit. State a probe's host before its result means
anything — and `rsync -az` preserves mtimes, so an old timestamp on a rendered file at the receiving end is
what a successful copy leaves behind, never evidence against the sync.

- `systemctl is-active keepalived` → `inactive`, `is-enabled` → `not-found`. That is **correct**: the standby's
  VRRP half is the `keepalived` **container** in `/opt/home-assistant-standby/docker-compose.yml`
  (`osixia/keepalived:2.3.4`), driven by `ha-failover.sh`'s `promote_vip()`/`demote_vip()` — there is no host
  unit to be active. The honest read is `docker compose -f /opt/home-assistant-standby/docker-compose.yml
  ps`, not `systemctl`.
- `/usr/local/sbin/ha-failover.sh` **is** installed and complete (forward = promote VIP then `up -d
  home-assistant`; reverse = `down` then demote), and it is the `ha_failover`-tagged half of
  `roles/home_assistant/tasks/standby.yml`. The script is ready; its subject is missing.
- `ha-config-sync.timer` read on the standby reads `not-found` and means nothing: the unit is deployed by
  `roles/home_assistant/tasks/pi.yml`, so it exists on the Pi alone. Read it there.

**Consequence, stated plainly:** **HD-418's standby-edge proof and HD-434's standby KNX tunnel have no subject
until a standby exists.** Both ask for a behaviour read *of the standby node* — a proxied request reaching
`home-assistant-standby`, a tunnel opened from it to `knx-ip` — and there is no such process on oldsrv to
observe. They are not blocked by a missing measurement technique, a router rule, or an owner ruling; they are
blocked by this row's cold leg. Any "proof" written against them before the create runs would be proof about
the Pi, relabelled.

The create itself is unchanged and owner-scheduled — `ansible-playbook IaC/ansible/playbooks/home_servers.yml
--limit oldsrv --tags ha_failover` (⛔ never `--diff`; its `authorized_key` task writes SSH keys on oldsrv) —
and note what it will *not* do: the role renders and creates, it never starts. The `enabled: false` registry
entry (`group_vars/home_servers.yml`) also means every unscoped `docker_services` converge runs
`docker compose -p home-assistant-standby ... down --remove-orphans || true` over this directory
(`roles/docker_services/tasks/main.yml`, *Tear down DISABLED services*), so the guard the row asks for is
still owed and becomes live the moment the container exists: while the standby **is** the running node, a full
converge stops the live HA. Re-derive the whole table with:

```bash
ssh oldsrv 'docker ps -a -q | wc -l; docker ps -a --format "{{.Names}} {{.Image}}" | grep -iE "hass|home.?assist|keepalived"; \
            docker images --format "{{.Repository}}:{{.Tag}}" | grep home-assistant; \
            grep -nE "image:|container_name" /opt/home-assistant-standby/docker-compose.yml; \
            systemctl is-enabled ha-config-sync.timer; ls -la /usr/local/sbin/ha-config-sync.sh'
```

## Remote & App Access (`ha.kogler.si`)

- **Route:** `ha.kogler.si` → Traefik → **VIP**. The `ha` route must **NOT** use Authentik Forward-Auth (breaks the Companion WebSocket/token flow) — see `smart-home.md`.
- **VIP↔edge coupling (hard requirement):** the VIP (`ha-vip`) is served on `:443` by whichever keepalived node owns it. In normal mode the Pi's **`traefik-ha`** edge serves `ha.kogler.si`; after takeover the home-LAN **internal all-app edge (`traefik-internal` on oldsrv)** serves it — both carry an identical `ha` route → VIP:8123, so `ha` keeps working through a Pi-out (see the edge model, [services-traefik.md](services-traefik.md) §Edge model). HA must not leave VLAN 10, and keepalived must keep the VIP on the active HA node — otherwise the `ha` route breaks (see `services.md` accessibility SSOT).
- **Normal (Pi active):** Android app works over WAN (Cloudflare → VPS Traefik) and over VPN (Headscale).
- **Fallback (oldsrv active):** same hostname routes to the standby. **WAN access is NOT required in fallback** (accepted) — app still works on LAN/WiFi, and over VPN if needed.
- **Security:** HA `http.use_x_forwarded_for: true` + `trusted_proxies: <all edges that front HA — Pi traefik-ha, oldsrv traefik-internal, VPS edges>`; one local `owner` account.

### Edge (`ha.kogler.si`) accessibility on node failure

> **The gap this closes:** `traefik` runs only on oldsrv → it is the single point of
> failure for the whole `:443`/TLS plane. The **Pi-down** case is covered
> (HA and Traefik sit on oldsrv, so after the manual failover
> everything incl. the `ha` route works). The **oldsrv-down** case is the real gap:
> HA + DNS survive on the Pi, but the only HTTPS edge is down.

**Design — HA's edge is co-located with HA and rides the VIP.** Run a minimal,
VIP-bound **`traefik-ha`** edge on the Pi that serves **only** `ha.kogler.si →
VIP:8123` (no Authentik Forward-Auth — same rule as the home `ha` route, it breaks
the Companion WebSocket/token flow), **plus** the home-LAN internal all-app edge
**`traefik-internal` on oldsrv** which serves `ha` + every internal app
when the VIP is on oldsrv. Because the VIP already tracks the active HA node, the
`ha` edge moves with HA automatically — **no DNS flip on failover**:

| State | VIP owner | Serves `ha.kogler.si` via… |
|---|---|---|
| Normal | Pi | Pi `traefik-ha` → local HA |
| Pi down (manual forward takeover) | oldsrv | **oldsrv `traefik-internal`** → VIP → standby HA |
| oldsrv down | Pi | Pi `traefik-ha` → local HA — gap closed |

### KNX tunnel reachability (constraint)

- The KNX reply leg must be accepted by **`src-port=3671 → trusted-ha`**, not only as `established/related`
  conntrack: an idle UDP tunnel that outlives the conntrack timeout stays permanently half-open and xknx
  cannot see it. Outbound keeps working, so the failure is silent — devices still answer commands while entity
  states freeze, `outgoing_telegram_errors` climb and `incoming_telegram_errors` stays `0`.
- ⚠ The probe that decides this class of failure is a **UDP** test: ICMP and TCP answers say nothing about a
  half-open UDP tunnel. "The GIRA router refuses the standby" and "`trusted-ha` was the cause" are claims,
  not findings, until that probe has been run.
- ~36 emitted state group addresses have no proven responder and keep timing out on every sync even on a
  healthy bus.
- The standby's KNX path is unproven — retest it at a drill with the primary as a known-good reference.

### Away access (tailnet)

- Each home box runs its own `websecure-ts` listener + `ha-ts` router and `ha`/`ha-ts` target the **VIP**, so a
  tailnet client keeps reaching HA whichever box owns the VIP — from inside the tailnet even when home's WAN is
  down. Home takeover is served by **`traefik-internal` on oldsrv** ([services-traefik.md](services-traefik.md)
  §Edge model); `ha.ts.kogler.si` / `oldsrv.ts.kogler.si` on its tailnet listener route to
  `ha-backend = VIP:8123`.
- ⚠ The weak half is the **answer**, not the edge: MagicDNS (the loopback resolver in
  [network-dns.md](network-dns.md)) answers a `.ts` name with the addresses its `zone_kogler_si` entry
  publishes, and a `tailnet: node` entry publishes **one** — oldsrv's, SSOT `tailnet_oldsrv_ip` — so while
  `ha` is `node` an away client gets a dead answer for the `ha`-shaped names whenever that node is silent and
  must reach HA as `pi.ts.kogler.si`. `tailnet: dual` publishes the Pi's address beside it
  (`tailnet_pi_ip`, second row rendered only when it is set); it is deliberately NOT a bolt-on to
  `tailnet_subdomains`, which would answer the PLAIN `ha.kogler.si` client-side for a phone standing at home.
  ⚠ **It is also gated on the Pi answering that name**: the Pi's `traefik-ha` serves Traefik's default
  self-signed cert for SNI `ha.ts.kogler.si` / `pi.ts.kogler.si` until its `tls.certificates` block carries
  the `.ts` pair and that edge converges, so flipping the field first turns half of all away clients into a
  TLS error ([network-vpn.md](network-vpn.md) §Tailnet boundary).
  Reasons: [network-dns.md](network-dns.md) §The answer-plane model.
- ⚠ A dual-A publish makes the **answer** survive either home box and does not make the **service** survive
  it. Both `ha`/`ha-ts` routers target the VIP, and the VIP has one advertiser until the standby is
  cold-created (§Nodes & Deployment) — `live-verified 2026-10-29`: the VIP answers on the Pi and oldsrv runs
  no `keepalived` — so the drill that proves failover is owed independently of the record.
- Plain `ha.kogler.si` deliberately does **not** resolve from away: publishing the internal home zone's answer
  publicly is the exposure the design refuses. **The coupling:** `ha.ts` is a `.ts` name, so its *resolution*
  lives in the netmap (headscale, VPS) while its *answer* is the VIP — it carries both dependencies. Same
  VIP↔edge coupling flagged for the media family in
  [network-addresses-generated.md](network-addresses-generated.md); here it is load-bearing for away access
  to the house.

### DNS survives one home DNS host dying

- The router advertises **three** resolvers on every DHCP network (Home: Pi → VPS → oldsrv), so a Pi-out does
  not leave the house unable to name anything. ⚠ **"The router points only at the Pi" is the claim to check
  before acting on it.** The real residual is per-VLAN, not global, and it is a question of which rows the
  device actually carries: a read of `ip firewall nat` chain `dstnat` shows **one** `:53` pair — the kids
  tablet MACs onto the **VPS primary** — while the IoT-VLAN-20 pair is **absent**, so IoT resolves by the
  ordinary three-server chain and loses nothing when the Pi dies. The Kids half is single-target as
  designed; the IoT half exists in the role and the converge template, not on the device, and its
  reconcile is parked with the router's VLAN-99 trunk parity
  ([network-dns.md](network-dns.md) §What the pin can and cannot enforce).
  ⚠ **The per-device query record does not depend on this map.** The Pi tertiary logs queries
  ([network-dns.md](network-dns.md) §Tier policy rulings) and its own log carries per-client lines whose addresses
  are in the IoT subnet — because the Pi is the **first resolver DHCP advertises**, so IoT clients ask it first
  with no NAT involved. What escapes both the steering and the record is a client that ignores its DHCP resolver
  (hardcoded `1.1.1.1`, DoT); that is the half the absent rows would have covered, so do not cite per-device
  coverage as complete.

### State to restore after a takeover

- After any forward takeover, oldsrv's **active** `keepalived.conf` holds the failover variant
  (MASTER, prio 120) and **nothing restores it on its own.** The `reverse` leg of `ha-failover.sh` copies
  the standby variant back; a converge deliberately cannot — the role bootstraps the active name with
  `force: false` so that re-converging never clobbers a live runtime swap, while the render task that *does*
  stay current writes the sibling `keepalived.standby.conf`. So a takeover that ends without `reverse`
  — a drill stopped after its forward leg counts — leaves oldsrv in the failover variant indefinitely. It is
  inert only while the standby is cold: the first cold start of the standby's keepalived raises
  MASTER/120 against a healthy Pi at 110, which is a self-inflicted takeover, not a failover. Restore it
  before the standby is created or started again.
- **Read the state before writing anything.** If the standby stack is running, or the VIP is on oldsrv's
  Home interface, that is a live or half-finished failover and not drift: leave the file alone and either
  finish the takeover or run `sudo /usr/local/sbin/ha-failover.sh reverse` — the heavier form that restores
  the same bytes *and* restarts keepalived, which is what a live failback wants and what an idle standby
  must not be given.
- The hand restore is the same copy `reverse` performs. Nothing needs to be running and nothing may be
  restarted for it: keepalived reads the file at container start, so the file only decides what the **next**
  start does. Keep the replaced file — the failover variant is the drill's artifact.

  ```bash
  D=/opt/home-assistant-standby
  sudo cp -a "$D/keepalived.conf" "$D/keepalived.conf.bak-$(date +%s)"
  sudo cp "$D/keepalived.standby.conf" "$D/keepalived.conf"
  grep -nE 'state |priority ' "$D/keepalived.conf"   # state BACKUP / priority 100
  ip -4 addr show dev enp0s31f6                       # oldsrv's own address only — no `ha-vip` in rest state
  ```

  Ownership/mode come from the source sibling (`root:root 0644`), which is what the compose's
  `./keepalived.conf:ro` bind expects; the two siblings must keep their own checksums.
- Prove the result without starting a daemon, using the keepalived image the standby compose already
  carries. In keepalived 2.x the config-test flag is `-t`; `-c` is `checkers_pid` and answers
  `Missing parameter for option -c`, which says nothing about the file.

  ```bash
  D=/opt/home-assistant-standby
  IMG=$(awk '/image: osixia\/keepalived/ {print $2; exit}' "$D/docker-compose.yml")  # the pin, not a literal
  docker run --rm --network host -v "$D":/chk:ro --entrypoint /usr/local/sbin/keepalived \
    "$IMG" -f /chk/keepalived.conf -p /dev/null -t && echo VALID
  ```

  A canary earns the verdict: the same invocation on a config with a non-numeric `priority` must exit non-zero.
- **There is no IaC guard on this drift, and there will not be one from the facts a converge can see.** The
  obvious assert — active conf is the failover variant **and** the standby is cold — is also true for
  seconds *inside* `ha-failover.sh forward`, which copies the failover variant in before the container that
  advertises the VIP is up; a converge landing in that window would read a real takeover as drift. Adding a
  staleness clause (conf unchanged for a day) closes that window, but the safety of what is left rests on a
  "is the standby cold" probe — container state plus VIP presence — and a probe that errors reads as cold,
  which is the one mistake that can demote the live node. So the restore stays a human step owned by the
  `reverse` leg and recorded here; `force: false` stays because a converge that could write this file is a
  converge that can demote whichever node is active.

**The same edge also serves the DNS-secondary web UI (`dns-pi.kogler.si`).**
`dns-pi.kogler.si` resolves to the **VIP** (FQDN shape borrowed from the cockpit
naming pattern, but delivery is like `ha` — NOT a file-provider route on oldsrv)
and is served by the Pi's `traefik-ha` edge → local `pi:5380` (IP per SSOT). Rationale:
when oldsrv is down, the Technitium instance on the Pi is the surviving DNS,
so its web UI must be reachable without oldsrv's Traefik. Internal-only, no
Forward-Auth. Direct fallback `pi:5380` on the LAN.

**Scope:** the Pi edge keeps **HA + the DNS-secondary web UI** reachable when oldsrv is down. The home-LAN **`traefik-internal` (oldsrv)** additionally serves **every internal app** (immich, Forgejo, grafana, …) on the LAN when WAN/VPS is down or the Pi is down (their backends are containers on oldsrv). When oldsrv itself is down, its hosted apps die with it (a second edge cannot rescue them) — HA and DNS are the only survivors (Pi edge).

### Caveats (implementation)

- **VIP-only bind / gating:** `traefik-ha` uses `network_mode: host` with entrypoints
  explicitly bound to the VIP (`ha-vip`):80/443, and the Pi sets `net.ipv4.ip_nonlocal_bind=1`
  so Traefik can bind the VIP before/without keepalived holding the address. Only the
  keepalived MASTER (Pi in normal mode) owns the VIP → `:443`, so it never fights
  oldsrv's `traefik-internal` for the VIP.
- **Offline-safe cert:** ACME is **disabled on the Pi edge** — it is not an ACME
  issuer. The wildcard `*.kogler.si` cert pair is **synced from the issuer — the single ACME issuer, the VPS
  Traefik** — to `/opt/traefik-ha/certs/` on a timer (`ha-cert-sync` pulls **directly from the VPS**; the Pi's
  `ha-sync` key must be authorized on the VPS ⏳).
  If the sync source is unreachable,
  the last synced cert still serves `ha.kogler.si` / `dns-pi.kogler.si` (ACME
  cannot renew, but it does not need to). The Companion app requires a valid cert, so it must work fully offline
  (WAN loss is not a failover trigger and is not required in fallback).
- **`trusted_proxies`:** HA must trust every edge that fronts it so real client IPs are preserved.
  `ha_trusted_proxies` (`group_vars/all/main.yml`) renders the list and includes the oldsrv Home-IP.
  ⚠ **The rendered `configuration.yaml` is not what HA enforces here.** Once the `http` integration has
  migrated its YAML into `.storage`, HA reads `http` from `<config>/.storage/http` and the YAML block
  becomes decoration: a value can be present in every rendered `configuration.yaml`, survive every
  converge, and still not be in the trust list the running process consults. Read the effective list
  from the storage object on the **active** node — `jq '.data["http"].trusted_proxies
  | to_entries[] | .value' /opt/home-assistant-primary/config/.storage/http` — and diff it against what
  `ha_trusted_proxies` renders. Extending `ha_trusted_proxies` alone does NOT change the running list:
  the storage object has to be reconciled, which is a config write plus a **restart** of the HA
  container (an owner-window act, not a converge side effect).
  ✅ **Reconciled 2026-10-19 on the active node:** `.storage/http` on the Pi now carries the full rendered
  `ha_trusted_proxies` list in BOTH `stable` and `pending` (the third entry, the oldsrv Home-IP, had been in
  the YAML for a month and absent from the object the whole time — HA's own log recorded `Received
  X-Forwarded-For header from an untrusted proxy <oldsrv home ip>`), owned in IaC by
  `roles/home_assistant/tasks/pi.yml` under the `hd418` tag, which backs the object up root-only with a
  timestamp and its hash, writes both blocks, restarts only the HA container and re-reads the object.
  Proof instrument unchanged: `200`/`401` = trusted, `400 untrusted proxy X` = names the missing address.
  ⚠ **Configured, not proven end-to-end from the standby edge:** the request that would settle it comes FROM
  oldsrv's own address, and oldsrv is not this lane's to run commands on — what was proven here is that HA
  honours `X-Forwarded-For` from an address on the list (the real client IP lands in its auth log) and
  refuses it from one that is not (`400` + `untrusted proxy <source>`), plus list equality with the rendered
  value. The standby half of the row has no subject while the standby is UNDEPLOYED (HD-1109).

## Forward Takeover (Pi → oldsrv) — MANUAL

**Prerequisites:** ⛔ **not met today — see the banner.** The standby must already be **created**; on this
fleet it is not, so a forward click cold-creates it. What is in place: `/opt/home-assistant-standby` with
its compose and a real `keepalived.conf` file (rendered by the `home_assistant` role), and the standby's
config kept current by the Pi-side `ha-config-sync.timer` (live, measured 2026-10-19). What is missing: the
cold `create` (`--tags ha_failover` on oldsrv, owner-window) and the pinned image on that host.

**Two manual actions total:** (1) confirm Pi down, and (2) fire **one** takeover trigger. Everything after the trigger is a single orchestrated script — no VIP / standby steps.

**Who fires it:** `ha-failover.sh` is the only mechanism, and the standing way to reach it is **root on
oldsrv**: `sudo /usr/local/sbin/ha-failover.sh forward`. The Homepage card is the **same** trigger behind a
web wrapper — `ha-failover-api` runs on oldsrv on `failover_api_port`, and the two cards render when the
group_var `homepage_failover_button` is true (`group_vars/vps.yml`; the gate exists so a card is never a
dead link).

> **What the card is, and where it works.** The href is the oldsrv **Home-VLAN** address —
> `failover_api_url` = `http://`*oldsrv home IP*`:`*`failover_api_port`* — plain HTTP, token in the query
> string (the card is a link, so GET is the only shape a browser gives it; `POST` + the `X-Failover-Token`
> header works too). The API binds `0.0.0.0` on the Home VLAN and **nothing publishes it**: no edge route,
> no `.ts` name, no TLS, no Authentik. So the card answers for a device on the home network — the family
> Kogler SSID is VLAN 10, the same L2 subnet oldsrv sits on, so there is no firewall hop to open — and it
> reaches **nothing from away**: away from the house the click just times out, and the SSH/root path above
> is the one that still works there. The token also lands in the rendered `services.yaml` on the VPS, so
> reading that file grants the ability to fire the trigger *from inside the home network* — the same
> accepted trade the API's own bind comment states. The click is **synchronous**: the API runs the script
> and answers when it exits, so the browser tab waits on the VIP hand-off (`promote_vip` waits up to 30 s
> for the address) before the response arrives.

1. **Confirm Pi is down** (human verifies — power, SD, OS, network).
2. **Fire the trigger** — `/usr/local/sbin/ha-failover.sh forward` on oldsrv, directly or from the
   Homepage card, which calls `ha-failover-api` to run the same script:
   a. promotes keepalived (Pi MASTER demoted / oldsrv BACKUP promoted → the VIP moves to oldsrv),
   b. starts `home-assistant-standby` (re-polls KNX/Shelly).
   The API reads its token from `/etc/ha-failover/api.env`, parsed like a systemd `EnvironmentFile` —
   **never shell-evaluated**, it contains shell-special characters — and answers
   `HTTP 200 {"event":"forward","exit":0}`.
   (If the VIP path is ever unavailable — HA OS fallback — the script additionally flips the Technitium `ha.kogler.si` record + the Traefik `ha` endpoint.)
3. Verify a live KNX **and** Shelly control command through the VIP; notify n8n → Signal/email and log the event (see `observability.md`).

> **Homematic note:** Homematic rides the cloud HAP, so failover covers the IP devices (KNX, Shelly) cleanly via the VIP; Homematic availability follows the vendor cloud, not the VIP.

## Reverse Failback (oldsrv → new/repaired Pi) — MANUAL

> ⚠ **Never auto-failback in a two-node VIP setup** — that is how split-brain happens. Prefer explicit manual transfer, especially because the standby has been running and holds **newer state** than a freshly-rebuilt Pi.

1. **Build the new Pi as a peer, not master:** run the `raspberry_pi` playbook → Pi comes up with the same config as **standby** (disabled VIP, no active role).
2. **Reverse the state sync (standby → Pi):** oldsrv (former standby) now has the freshest config/DB; push it to the new Pi so no family/lights config is lost. (Normal sync direction is Pi → standby; reverse it here.)
3. **Drain the standby:** put it in maintenance (disable its VIP/watchdog), confirm the new Pi is healthy and can control a live device.
4. **Flip the VIP back** to the Pi (manual button/script).
5. **Mark Pi = primary**, oldsrv returns to cold/disabled.
6. **Drill:** exercise forward + reverse, and re-test annually with the backup restore drill (see `backup.md`).

## Config & State Sync

- **Source of truth:** this repo (config already lives here). The standby is healthy when its rendered `/config` matches the repo + a recent Pi snapshot.
- **Normal direction (Pi → standby):** local push of `/config` to oldsrv on a timer (e.g. every 15 min), LAN-only, no WAN dependency.
- **HA recorder DB — local primary, remote copy by rsync:** the recorder stays on the Pi as **local trimmed SQLite** (always available, survives oldsrv-down; `purge_keep_days: 1–2` per `observability.md` *Pi SD-card wear strategy*). A periodic **rsync** of the SQLite file Pi → `/opt/home-assistant-standby/config/` (~15 min, ~few MB) is the **only** remote copy, not a failover primary. On standby takeover HA reads the synced copy (best-effort) and re-polls devices; durable long-term analytics live in Grafana (VictoriaMetrics, 365d), not in the recorder DB. Putting the recorder's only database on oldsrv (Postgres) or on a VPS (Postgres) would make HA history depend on a remote host — violating the *Pi survives oldsrv-down* property and the *no WAN on critical path* rule; **local-primary + remote-rsync** gives the same durability without that coupling, and trimming already defends the microSD (see `observability.md`). The alternative is in the decision log ([smart-home-rejected.md](smart-home-rejected.md)).

## Shelly / MQTT Note

- No MQTT broker exists in the design — Shelly are connected via HA's **native Shelly integration** (direct LAN HTTP/WebSocket per device), so **no broker is a failover surface**. The standby talks to each Shelly directly on takeover.
- If MQTT is ever added (e.g. a rocker switch), run a **Mosquitto** container on oldsrv and give it a stable address reachable by whichever HA is active.

## HA VIP (address / notation / firewall IP-set)

> Single source of truth for the value: `group_vars/all/` (`ha_vip`, `ha_vip_cidr`).

- **Address:** `ha-vip`, a single `/32` — keepalived VRRP VIP on Home VLAN 10; `ha.kogler.si` → VIP. Value lives only in the SSOT + config templates.
- **Reservation:** single `/32`, **no reserved block**. Home DHCP pool stays ≤ `.199` (pool per SSOT); never extend it into the VIP or assign `ha-vip` as a normal static lease.
- **Naming:** canonical name **`ha-vip`** everywhere (SSOT host row, keepalived, Technitium A records, docs). Ansible vars **`ha_vip`** + **`ha_vip_cidr: 24`** live in `group_vars/all/` only; all templates consume `{{ ha_vip }}` — the literal value appears only in `group_vars/all/` and the rendered SSOT.
- **Firewall IP-sets (RouterOS):** the VIP belongs to the **existing** address-lists in `rb4011_initial.rsc`:
  - `trusted-admin` — Home→Mgmt rules (SSH/WinBox/API)
  - `trusted-ha` — Home→IoT rules (MQTT/HA, KNX/Shelly trusted-IP). No dedicated `ha-vip` list.
