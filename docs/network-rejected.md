## Decisions

| mDNS reflection (RouterOS mDNS repeater / Avahi across VLANs) | rejected | 2026-08-23 | Cross-VLAN mDNS re-couples the broadcast domains the VLAN plan exists to separate; no integration needs it — cloud appliances (LG ThinQ / Bosch Home Connect) pair via vendor apps + cloud APIs with zero cross-VLAN rules ([smart-home.md](smart-home.md) §Cloud Appliances), local devices (Shelly Gen1 CoAP, KNX gateway, ESPHome) are added by static host/IP with DHCP reservations. Decision context HD-228. · [smart-home.md](smart-home.md), [network-vlans.md](network-vlans.md) |
| DNS primary placement (oldsrv vs VPS) | superseded | 2026-09-03 | **HD-317 / HD-299 executed (2026-09-03):** the DNS primary moves from **oldsrv to the VPS** — 3-instance DNS HA (**VPS primary / oldsrv secondary / Pi tertiary**, separate physical hosts). Rationale (owner + AI, 2026-09-03): the VPS is always-on + WAN-reachable; a DNS primary there keeps LAN + tailnet resolution independent of home infrastructure (oldsrv was offline at decision time; the plain `*.kogler.si` tailnet names resolve via the VPS primary). **Option A (supervisor decision):** single resolver address `dns_primary_ip` = **VPS public IP 159.195.111.66** (LAN hairpins via the HD-309 WAN egress; tailnet resolves it too; survives a WG-tunnel drop). Abuse surface (public UDP 53) is mitigated by strict **VPS nftables source-allow** (tailnet headscale CGNAT + a `dns-allow-home` set refreshed by an Ansible-managed systemd timer that re-resolves the home DDNS `s.kogler.si` every 5 min) — the home-WAN source is DDNS, so drift is self-healing. Alternatives declined: **Option B** (LAN uses the WG S2S bind `10.255.40.2:53` + tailnet uses the public IP) — split resolver addresses + dies with the tunnel; **Option C** (keep primary on home) — contradicts the goal. oldsrv/Pi keep the home-LAN failure-domain split (WAN-out / VPS-down). · [network-dns.md](network-dns.md), [todo.md](../todo.md) HD-317 |
| per-purpose SSID per VLAN (5 SSIDs: Kogler/IOT/IOT-WAN/guest/kids) | superseded | 2026-09-03 | **HD-312 decision (2026-09-03):** the per-purpose-SSID wireless model is superseded by a **3-SSID consolidation — Kogler (family + kids, VLAN 10), IOT (VLAN 20 + per-device WAN via MAC-based list, client-isolation), Kogler guest (VLAN 30, 5GHz, client-isolation)**. Rationale (owner + AI, 2026-09-03): the 2.4GHz band had 5 SSIDs (airtime waste — an AI audit of the live state flagged this); every device has an all-static MAC in `network_static_hosts`, so **per-MAC control** (CAPsMAN `access-list` vlan-id + firewall MAC-address-lists) is strictly better than SSID-per-purpose. Merges: IoT + IoT-WAN → one IOT SSID (cloud-IoT = permanent `iot-wan-allow` MAC list; a firmware window = temporary list add/remove — enables the n8n monthly automation); Kids → into Kogler (same network, family sees each other; kids controls become firewall MAC-address-list, not VLAN 40); Guest stays a separate SSID (unknown guests can't be MAC-mapped). `access-list` on wifi-qcom-ac 7.24.1 supports per-MAC `vlan-id` (live-verified) but cannot move a client to another SSID; requires the CAP bridge access-port pvid model (already in place from HD-229/310). n8n firmware automation (owner idea) toggles the temporary WAN via the router API `iot-wan-allow` list over the wg-s2s tunnel. · [network-vlans.md](network-vlans.md) §3-SSID, [todo.md](../todo.md) HD-312 |
| netplan | rejected | 2026-08-16 | Host network config-manager — Ubuntu-desktop default + extra python3/libnetplan translation layer; rejected in favor of native `systemd-networkd`. HD-56. · [network.md](network.md) |
| systemd-networkd (on RPi Pi) | superseded | 2026-09-01 | The 2026-08-16 netplan-rejection recorded `systemd-networkd` as the repo's config-manager, but the live Pi (Raspberry Pi OS / Debian trixie) ships **NetworkManager** (cloud-init `renderers/activators: netplan, network-manager`; NM 1.52.1 active; no systemd-networkd). Implementing the networkd unit as written would disable/fight NM and risk severing the remote session. **Pi host-side dual-home is therefore done via two NetworkManager keyfiles** (HD-311 refined 2026-09-02): `pi-eth0.nmconnection` = untagged Home on the parent (`ansible_host`, default via Home — single gateway, no `never-default`; DNS via `bootstrap_dns_servers`) + `pi-mgmt.nmconnection` = tagged Mgmt on the `eth0.99` sub-interface (`mgmt_ip`, never-default, route via the tagged leg). The Mgmt IP lives ONLY on the tagged sub-interface — the untagged parent cannot reach the Mgmt plane (ether10 pvid=10), and its stale connected route hijacked `mgmt_subnet` lookups away from the tagged leg (`router99` 'No route to host' live 2026-09-02, fixed + verified). desktop/VPS hosts keep systemd-networkd where that is their manager. HD-307/HD-311. · [network-vlans.md](network-vlans.md), [roles/network](…/IaC/ansible/roles/network/) |
| systemd-networkd (nas/oldsrv netd units) | accepted | 2026-09-02 | **nas + oldsrv (desktop/VPS class) use systemd-networkd** for static dual-home: physical `.network` (untagged Home 10 + default route), `.netdev` VLAN-99 tagged sub-interface, and its `.network` (Mgmt IP, connected-only). Rendered by the `network` role (HD-311). Pi remains the NetworkManager exception (2026-09-01 row). · [network-vlans.md](network-vlans.md), [roles/network](…/IaC/ansible/roles/network/) |
