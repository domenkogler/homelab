> **Role:** the owner window's record — the baseline it started from, the two converges it ran, the
> import-time failure that ended it, and the rollback that left the box serving `fast`.
> **Linked from:** [`../README.md`](README.md) §7b · [`todo.md`](../../../todo.md) HD-1206 ·

**Verdict: BLOCKED — the v32 artifact (`spark-ultrafast:v32-iter6d`, `72eb432fd87c`) cannot serve.**

## 3. Why it cannot boot: the PLE-mmap overlay requires a method the base no longer has

Three reads, each in the image, read-only:

| read | where | result |
|---|---|---|
| `forward_impl` anywhere in the `qwen4_exp` tree | `spark-ultrafast:v32-iter6d` | **0 occurrences** |
| the class the hook is applied to | `ngram_embedding.py:44` `class Qwen4ExpNGramEmbedding(nn.Module)` | defines `forward` at `:374`; **no `forward_impl`** |
| the hook | `vllm_ple_mmap.py:996-997` | `cls._ple_mmap_orig_forward_impl = cls.forward_impl` then `cls.forward_impl = forward_impl` — it rebinds a method **by that name** |
| the overlay's own contract | `vllm_ple_mmap.py:18` | "``forward_impl`` (hashing + lookup) is wrapped in a custom op" |
| the base at the pin digest | `vllm/vllm-openai@sha256:6ff5ff0d…` | `forward_impl` in `ngram_embedding.py` → **0**: the rename is upstream's, not the port's |

So the day-0 overlay wraps a method named `forward_impl`, and at v0.32 the n-gram embedding exposes `forward`.
`apply()` reaches `cls.forward_impl` unconditionally at import time, so the failure precedes any config
decision: no profile value, pool size or dtype can change it.

`vllm_ple_mmap.py` is **not** the day-0 file either — `sha256` `ac4b7e59…` here vs `f9ef1c11…` in
`spark-rollback:fast`, i.e. the porter did run over it. The porter's anchor table
(`roles/spark-profile-fast8/files/port_v32.py`) re-points the module path, `Qwen3_8FlashNextModelState` →
`Qwen4ExpModelState`, `Qwen3_8FlashNextNGramEmbedding` → `Qwen4ExpNGramEmbedding` and
`Qwen3_8FlashNextPLELayer` → `Qwen4ExpPLELayer`. **It carries no anchor for the `forward_impl` → `forward`
method name**, and nothing in the set greps for it, so the build had nothing to stop it.

This is the class of gap [`README.md`](README.md) §7b's disposition ruling names: an anchor that lives as a
**string** inside an unchanged patcher, which a build can only catch by counting it. What the ruling requires
is the anchor, not a rewrite of the overlay.

**Why the post-build CPU gates pass on an unbootable image:** they assert day-0 bytes, so against v0.32 bytes
they certify nothing in either direction — the same fact [`todo.md`](../../../todo.md) HD-1206 already carries
and HD-1210 owns. A green CPU gate is not a boot.

## 5. Step 2 — the A+ runtime dispatch check, and what this failure does and does not falsify

The check asks whether a real bf16 GEMM lands on the `(12, 1)` plan or falls back to
`torch.nn.functional.linear`. Four legs:

| # | leg | verdict | evidence |
|---|---|---|---|
| 1 | device capability | **MEASURED = (12, 1)** | `nvidia-smi --query-gpu=compute_cap,name` → `12.1, NVIDIA GB10` |
| 2 | a plan exists for the weight shape | **MEASURED** | in the image: `QWEN4_EXP_GEMM_PLANS_BY_CAPABILITY` keys `[(9,0),(10,0),(10,3),(12,1)]`; `QWEN4_EXP_SM121_GEMM_PLANS` carries **16** shapes, and `(1280,2560)`, `(640,2560)`, `(1,2560)`, `(96,2560)` each resolve with an M=1 `SkinnyGemmConfig` — [`raw/dispatch-image-legs-20261103.txt`](raw/dispatch-image-legs-20261103.txt) |
| 3 | `_runtime_ok(x, weight, config)` | **NOT MEASURED — inferred** | needs live bf16 CUDA tensors of the plan's own shape; only a booted engine has them |
| 4 | `shape_dynamic_skinny_gemm.is_available()` | **MEASURED True** | same read; `cutlass`/`cutlass.cute` import in the image, so the leg is not the blocker |

**Verdict on the dispatch: UNRESOLVED — not a pass and not a fallback.** Legs 1, 2 and 4 are each satisfied,
so the plan machinery is sound and nothing about it is falsified here; but leg 3 is exactly the leg that needs
a booted engine, and **no engine ever booted**: the import failure at `ple_layer.py:453` happens while the
registry inspects `Qwen4ExpForConditionalGeneration`, so the model class was never constructed and the
`(12, 1)` plan was never exercised. Whether the plan is reached at runtime remains unmeasured, and the read
that settles it is [`runtime_dispatch.py`](runtime_dispatch.py) on a booted v32 engine.

⚠ A GPU-less `docker run` cannot answer leg 1: `current_platform.get_device_capability()` reads `None` there,
so the plan-table key has to come from the box (`nvidia-smi`) and the dispatch from a booted container. The
image read is evidence about the artifact, never about the dispatch.

## 9. A second finding, from this window's own instrument: a child journal is outside the masker

Two `docker logs` reads of the looping container (the engine's `non-default args:` line prints its own argv,
`--api-key` included) put a CURRENT vault value into this run's subagent event journal,
`/tmp/pi-subagents-uid-1000/async-subagent-runs/2728f1c5-…/events.jsonl`. `check_secret_leak.py` reports it
as a `run-capture` hit for item `h7fi4x62`.

**The leak class is documented; the masker hole is not.**
[`docs/deployment-ai-stack-secrets.md`](../../../docs/deployment-ai-stack-secrets.md) §4a already states that the
vllm boot log prints the argv it was started with and `--api-key` is in that argv (HD-1170 carries the same
class). What is new is that a **child subagent's journal re-emits those bytes untransformed**.

| read | result |
|---|---|
| the masker's hook surface | [`pi-agent/extensions/vault-mask.ts`](../../../pi-agent/extensions/vault-mask.ts) hooks exactly one event, `pi.on("tool_result", …)` at `:280`; the string `tool_execution` appears **0** times in that file |
| the child journal | the value is reachable through **six** event types — `tool_execution_start`, `tool_execution_update`, `tool_execution_end`, `message_start`, `message_end`, `turn_end` |
| the control | the parent session's journal carries **0** hits — the masker does mask the parent's `tool_result` path, so the difference is the event family, not the value |
| the same file's masked events | line 70 carries `[vault-mask:…]` tokens, i.e. the masker works on the `tool_result`-shaped events in that very file and misses the execution/journal family beside them |

So masking is live where the extension hooks and absent where the journal is written, and any `docker logs`
read crossing that boundary in a child lands raw. That is a property of the harness, reproducible, and it
belongs to **HD-1216** (`vault-mask.ts`), which owns the masker's seam — not to this lane, and not to a fix
taken here. Per the rule the repo already applies to captures, the exposure is closed by rotation, not by
deleting a transcript; nothing was shredded and no ledger line was rewritten.

What this lane did verify about its own artifacts: `check_secret_leak.py --tree-only` is **OK**, `git status`
carries only this window's evidence files and `todo.md`, and neither of them contains an argv, `api-key`,
`Bearer` or token string.

## 10. What is owed

1. A rewrite of the overlay's install hook — a `forward_impl` → `forward` anchor alone is not enough. At v0.32.0,
   `vllm/models/qwen4_exp/nvidia/ngram_embedding.py` changed every member the day-0 `apply()` replaces:
   `__init__` takes keyword-only `data_parallel_rank` / `use_sequence_parallel` and no `max_num_reqs`; the table
   is built by `Qwen4ExpPLEDeviceEmbedding` / `Qwen4ExpPLEPinnedHostEmbedding`, and `VocabParallelEmbedding`
   (the class the hook swaps for its placeholder) occurs 0 times in that module; and `forward` hashes through
   `compute_ngram_ids` itself. A rename moves the failure from import to the first layer's construction.
   blazux/qwen3.8-Flash-DGX `src/vllm_ple_mmap.py` `_install()` (Apache-2.0) is a working port of the same
   hook onto exactly this layout; adopting it replaces install code rather than re-anchoring it, which is
   the owner's call under §7b's ruling.
2. A rebuild of the v32 lineage into a NEW tag (never in place), then the flips in the order
   `fast-v32-bf16` → gates 0–7 → `fast8` → gates 8–9.
3. The owner's `tailscale-spark_api` mint, so a full `playbooks/spark.yml` stops being refused.
4. The masker's seam, on HD-1216: the child journal's event family is outside `tool_result`.
