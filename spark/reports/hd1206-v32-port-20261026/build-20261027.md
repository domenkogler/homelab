## 6. 2026-10-27 — the post-build CPU gates assert day-0 bytes, so on this lineage they certify nothing

This is the finding, and it is a fact about the fixtures, not a mystery about the patch set.

Upstream's CPU self-tests re-run against the built tag do not ask "is this patch set coherent on
this base?". They ask "does reverting the recorded hunks reproduce the **day-0 base file**, byte for
byte?". On the day-0 lineage that is a real proof. On a v0.32 base the day-0 bytes are not the
starting bytes, so the same assertion is unfalsifiable in one direction and false in the other — and
`patch_block_drop.py`'s own run output says so before any assertion runs: `already applied to
speculative.py, scheduler.py, kv_cache_utils.py, single_type_kv_cache_manager.py, manager.py,
scheduler.py` (`applied OK to worker.py`).

`Run the block-drop CPU gate in the built image (both knob arms)` — `tests/test_block_drop_cpu.py`
against `tests/blockdrop_base_sha256.json`, both `VLLM_KEEP_DRAFT_BLOCKS` arms, `rc 1`, **17 `[FAIL]`s
each, identical across the arms** (the knob changes the latch, not the bytes). The fixture names the
base it was taken against, and it is not this base — the gate's own G1/G2 header prints it:

**Nothing was weakened.** No assertion, fixture or test was edited, skipped or `xfail`ed by this

**What a v32-shaped re-anchor would need**, stated as a shape and not as a change: a fixture derived

a stub carrying `block_size`), and for the three R3 markers in `[1]`, which want the plan-table

not this one — it belongs in a row, and minting one is not this report's to do.
