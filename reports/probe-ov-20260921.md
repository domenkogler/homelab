# OpenViking probe on the homelab corpus — 2026-09-21

Ephemeral lane per the `prompt-OV.md` brief, kept at the repo root as this lane's provenance — its
pre-registered gates are what make these numbers comparable. Follow-on lane brief: `prompt-agentmemory.md`.
Everything ran on `oldsrv` as the `domen` seat, in a venv,
against LAN-only models. Nothing was installed permanently and nothing in IaC was touched.
Raw evidence (configs, every measurement script, JSON outputs, server logs) is in
`reports/probe-ov-20260921/` (49 files); this file is the interpretation.

---

## 1. Verdict

**Row 1 of §8: Build rag-mcp. OV may still be trialled for memory only.**

The retrieval axis is genuinely good — OV answered 8/10 known-answer questions at ~5.3k
tokens per question where a `grep`+read baseline needed ~92k (17.5× more). The storage axis is
disqualifying for a git-backed corpus: OV does not store your Markdown. It replaces each file
with a directory tree named after the file's H1 title, re-chunks it, and **loses content** —
only 12 of 51 files came back byte-identical, and 20 of 51 had less than 95% of their lines
recoverable from the index even after I removed the embedding-failure cause.

And the thing OV sells on top of retrieval — the L0/L1 compile — is the worst result of the
lane: `spark` spent **120,469 prompt / 40,308 completion tokens and 14 minutes** to summarise
163 KB of docs, and produced a *worse* retrieval key than the free local extract (arm (c),
0 tokens, 154 tokens of text/doc, 18/20 usable keys vs 1/16, 0 invented facts vs 1).

## 3. Wire and config truths (none of these are in the brief)

- **`ov.conf` is JSON, not TOML.** `openviking init` does not exist (`ov` CLI has no `init`; the
  server has no `doctor`, and no `--data-dir` flag — the brief's assumptions are wrong).
- **`${VAR}` expansion works in `ov.conf`** → the LiteLLM key was injected as `LITELLM_KEY` from a
  `0600` file and never written into the config.
- **`extra="forbid"` on every config model** — any invented key is a hard startup error, which
  makes discovery cheap but unforgiving.
- **Embedding config nests under `dense:`** (`embedding: {dense: {model, api_key, ...}}`); a flat
  `embedding.model` fails validation.
- **`ov` CLI needs `ovcli.conf`** (env var `OPENVIKING_CLI_CONFIG_FILE`) and `ov language en`
  (Slovene locale otherwise crashes it).
- **Slot wire formats**: embeddings need the provider prefix (`openai/bge-m3-vk`; bare name =
  400). LiteLLM ignores `encoding_format`, so there is **no base64 trap** (HD-423's trap #1 does
  not fire). Rerank is called with the **Jina** wire format → the row must be declared
  `custom_llm_provider: jina_ai` (HD-425's trap #3 does fire exactly as described).
- **HD-387 answered: thinking does NOT have a `vlm.thinking` key in OV** — there is no such field.
  `extra_body` is accepted by the schema and **silently dropped** (never serialized). The working
  path is `extra_request_body: {"chat_template_kwargs": {"enable_thinking": false}}`, which
  survives the LiteLLM hop: reasoning tokens 26 → 0 on an identical request.
- **Split DNS bites**: `llitellm.kogler.si` does not resolve on `oldsrv` (resolver 1.1.1.1) —
  must use the LAN IP `http://10.10.1.30:4000/v1`.
- **`*-generated.md` exclusion works** (`--exclude "*-generated.md"`, proven on a toy corpus) and
  is persistable as `upload.exclude` in `ovcli.conf`.

## 4. P1 — does OV store Markdown faithfully? **No.**

Storage model decoded: a `.md` file becomes a **directory named from its H1 title slug** (the
filename is gone; two docs with the same H1 collide visually), plus one leaf per section, plus
injected `.abstract.md` / `.overview.md`. Code/YAML files keep their own name as the node.
Chunks live only in the vector store (`fs/ls` will not show them; read them via
`/api/v1/debug/vector/scroll` + `/api/v1/content/read?uri=&raw=true` — and note the `uri` filter
on scroll returns nothing, so dump and filter client-side).

Two runs of the same 51 files, `processing_mode=vectors_only`:

| `embedding.max_input_tokens` | chunks rejected | byte-identical (C1) | ≥0.95 coverage | zero chunks |
|---|---|---|---|---|
| 2048 (brief's value) | 91 / 510 (17.8%) | 12/51 | 15/51 | 9/51 |
| 1200 (my fix attempt) | 54 / 510 (10.6%) | 14/51 | 18/51 | 8/51 |

Fidelity split by *why* content is missing (cap=1200 run, failures attributed by URI prefix):

| class | n | front-matter | headers clean | pipes clean | fences equal | diacritics equal |
|---|---|---|---|---|---|---|
| coverage ≥0.95 | 18 | 12/12 | 17/18 | 17/18 | 18/18 | 18/18 |
| 0 < coverage < 0.95 | 25 | 10/17 | 6/25 | 12/25 | 15/25 | 14/25 |

So: **when a file survives intact, OV is byte-faithful** (front-matter, headers, pipes, fences and
Slovene diacritics all pass). The failures are not a reflow problem — content is dropped:

- 7 files lost content with **zero embedding failures**, i.e. attributable to OV's own sectioning:
  `reports/changelog.md` (50 embedded chunks, 33% of lines recoverable),
  `docs/network-addresses-generated.md` (37%), `skills/mikrotik/SKILL.md` (68–74% across runs),
  `reports/Qwen-bugs.md`, `reports/Qwen-architecture.md`, `spark/BENCHMARK-PLAN.md`,
  `brainstorming/recent/agent-memory-dev.md`.
- Worked example (`skills/mikrotik/SKILL.md`, cap 2048): 197 of 261 non-blank lines absent from the
  index, and `grep -rl "MikroTik Skill"` over all 265 stored chunks finds **nothing** — the text was
  dropped, not rewritten.
- Reversibility: the filename is not recoverable from the URI for Markdown (title-slug dirs), so an
  "index you can diff and reverse to the source" is out.

**Blocker #2 confirmed and made worse**: `max_input_tokens` does **not** protect a llama.cpp leg
with `--parallel/--ubatch 2048`. At cap 2048 the rejections were at 2055–4036 real tokens; at cap
1200 they were still at 2059–2173. OV's token estimate is ~40% low for this tokenizer, so the cap
cannot be set safely — the failure moves, it does not disappear. Fix belongs in IaC (raise the
leg's batch) or in OV (use the leg's tokenizer).

## 5. P2 — retrieval vs `grep` on the identical slice **OV wins on cost, loses on nothing**

10 known-answer questions with answer substrings (`questions.json`); both engines scored over the
same 51-file slice; `grep` baseline = keyword hit → read top-3 whole files.

| engine | hit@5 (right file) | answer in context | mean latency | mean tokens/query |
|---|---|---|---|---|
| OV `find` | **8/10** | 9/10 | 0.065 s | **5,267** (52,669 total) |
| grep+read | 5/10 | 10/10 | 0.042 s | 92,004 (920,044 total) |

Reads: **17.5× fewer tokens** for the same job, and faster wall-clock than is meaningful (on a
1.9 MB corpus grep is already 40 ms — the real cost of grep is agent context, and 92k tokens is
35% of a 262k spark session per question). Two honest caveats: grep's `answer in context = 10/10`
is a constructed property (it reads whole files), and OV's one miss (Q3, KV pool 515,786) traces
directly to P1's rejected chunks — `docs/hardware-spark.md` is one of the 9 files with zero
embedded chunks. P2 is therefore a *conditional* win: OV's retrieval is as good as its index, and
its index silently drops the long files where the answers live.

## 6. P3 — are spark L0/L1 good retrieval keys? **No, and the free version is better.**

Same 20 documents, same rubric (`p3_score.py`: R1 subsystem named, R2 hostnames clean,
R4 no invented facts, R5 usable as a retrieval key = H1 + ≥3 rare terms shared).

| arm | docs | R1 | R2 | R4 | R5 | mean summary | cost | wall-clock |
|---|---|---|---|---|---|---|---|---|
| (a) spark, thinking **off** | 16/20 | 16/16 | 16/16 | 15/16 | **1/16** | 3,548 ch ≈ 887 tok | 120,469 in / 40,308 out | ~14 min |
| (b) spark, thinking **on** | — | — | — | — | — | 66,943 in / **69,112 out** | **2 h 31 min, still 2 tasks running → killed** |
| (c) local extract, free | 20/20 | 20/20 | 20/20 | 20/20 | **18/20** | 616 ch ≈ 154 tok | 0 tokens | <1 s |

- Arm (c) was re-scored on the **identical** 20-document list (`p3c20.json` in the evidence dir),
  so (a) and (c) are apples-to-apples: same docs, same rubric, same rare-term extraction.
- Arm (a) also **failed to produce tiers for 4 of 20 docs** (no `.abstract.md`/`.overview.md` leaves)
  and invented one fact (`R4 15/16`); arm (c) invented nothing and covered all 20.
- Arm (b) is the OQ-10 answer: thinking ON inverts the token ratio (in:out 1:1.03 vs 3:1) and
  made 20 small docs take >2.5 h without finishing. **Never enable thinking in the OV compile path.**
- Fair-minded caveat on R5: it is a *lexical* key test. OV's intent is semantic (vector) retrieval,
  where a paraphrase is not automatically worse. What is not arguable: arm (a) cost 887 tokens/doc
  vs 154, and 5.8× the context for the same R1/R2 result and a worse R5.

## 7. P4 — compile cost and KV contention **This is the wall.**

| measurement | value |
|---|---|
| 51 files / 1.9 MB, `vectors_only` | **14 min** (embedding-bound), 510 chunks, 91 rejected |
| 51 files / 1.9 MB, semantic, `max_concurrent=1` | **>2 h and incomplete**; cumulative 459,827 prompt / 67,303 completion; decode ~11 tok/s |
| `max_concurrent` 1 → 3 | same 240-token call: 240 s → 46 s (**~8×**), aggregate ~45 tok/s |
| 20 docs / 163 KB, semantic, concurrency 3, thinking off | 14 min, 120,469 in / 40,308 out ≈ **740 prompt + 250 completion tokens per KB** |
| idle spark 16-token request | **0.27 s** |
| same request during compile | **8.7 s (32× slower)** |

Extrapolation to the whole repo (228 tracked `.md`, 5.1 MB, 31× the P3 slice): ≈**3.8 M prompt /
1.25 M completion tokens**, ~7–8 h at concurrency 3, ~30 h at concurrency 1 — on the same engine
that serves coding lanes, which it slows 32× while doing it. Re-compiles after corpus edits cost
the same (OV does incremental `fs/rm`+re-import only if you tell it to; no cheap "only changed
files" path was found).

Other reliability findings:
- **`--wait` is broken**: `add-resource --wait` dies at a 60 s HTTP read timeout
  (`ClientTimeoutError`) while the task keeps running server-side; `ov wait <id>` and `--verbose`
  hit the same timeout, and `task_id` is not printed with `--wait`. `--no-wait` returns a task id,
  but semantic tasks were never observed to reach a terminal `completed` state in `task status`
  even after the queue drained — you must poll `ov status` queue counters instead.
- **Crash resilience is fine**: SIGKILL mid-compile → restart clean, 677 vectors intact, no
  corruption; but queue error counters reset and in-flight work is silently lost.
- The token endpoint (`/api/v1/console/tokens`) reports `embedding_input` as a broken constant and
  resets when the data dir is replaced — treat per-run deltas as the only trustworthy figure.

## 9. OQ-1 … OQ-10

1. **Storage shape** — derived tree, not files: Markdown → directory named from the H1 slug (filename lost) + section leaves + injected `.abstract.md`/`.overview.md`; code/YAML keeps its stem. Chunks exist only in the vector store. Not git-diffable, not reversible.
2. **Fidelity** — FAIL overall (12/51 byte-identical at cap 2048, 14/51 at 1200). PASS conditionally: every file that stays intact passes front-matter, header, pipe, fence and diacritic checks. Loss is provably in OV's sectioning for 7 files with zero embedding failures.
3. **Retrieval quality** — better than grep on the metric that matters (17.5× fewer tokens, 8/10 vs 5/10 hit@5), as long as the answer is in an embedded chunk. The brief's 6/10 floor for grep was met by grep at 5/10 — i.e. grep is genuinely weak here, the comparison is honest.
4. **L0/L1 value** — negative. Thinking-off summaries cost 887 tokens/doc, invent a fact once in 16, and beat the free 154-token extract on nothing; thinking-on is unusable (2.5 h, 20 docs, unfinished).
5. **Compile cost** — ~740 prompt + 250 completion tokens per KB of docs, ~14 min per 163 KB at concurrency 3; whole repo ≈ 3.8 M/1.25 M tokens and 7–30 h.
6. **KV contention** — real and severe: 32× latency inflation on the shared engine during compile.
7. **Ops surface** — acceptable while healthy (single binary, venv, one port), but `--wait`/`task status` are unreliable enough that you must build your own completion polling, and error counters reset on restart so silent partial imports are easy to miss.
8. **Secrets** — no OV-owned secrets needed. LiteLLM key via `${ENV}` in `ov.conf` (never on disk); server runs `auth_mode: dev` bound to loopback. Note: the `litellm_api` 1Password item is the **master/admin** key (can mint keys), which sits awkwardly with HD-409's "`domen` seat holds no secrets".
9. **Scope** — worth keeping **only** as the agent-memory/session-tier layer on a small, self-managed corpus. Not worth it as the corpus index for 228 tracked files.
10. **§8 decision row** — **row 1: Build rag-mcp; OV may still be trialled for memory only.** The row-2 alternative ("adopt but skip the LLM compile") is explicitly killed by arm (c): if you skip the compile, OV's remaining advantage over grep is the vector index — which is exactly what `rag-mcp` already provides without a compile step, without losing files, and without a 3.8 M-token ingest.
